# 实验运行与续跑

用于已授权的长实验启动、接管、续跑或恢复验收。优先用项目现有训练入口、作业系统和 Checkpoint 协议；以下方法可用现有日志、配置和产物实现，不要求新建注册表、脚本或调度器。

## 把运行与启动尝试分开

- 用现有运行记录绑定 `run_id`、实际命令和已解析配置、代码版本（含影响本次运行的未提交变更）、数据版本或合成定义及切分、种子、环境及依赖、计算资源和输出目录。日志、Checkpoint 和结果须能追溯到这个身份；启动时间与进程／作业 ID 标记每次尝试。新尝试可延续同一运行；改变实验定义时按项目规则另设运行身份。
- 复用已验证的解释器、依赖和命令。启动或接手时增量查可用资源：例如 GPU 占用、磁盘余量、数据可读性、相关作业和输出写入权。一个运行目录只保留一个有效写入者；仅凭旧 PID 不足以认定进程仍属于这次尝试。
- 从进度、心跳、作业状态和最后有效产物判断。作业仍在且有近期活动可报 `RUNNING`；按要求产出并核对结果后才报 `COMPLETED`；异常退出或结果验收失败报 `FAILED`；必要输入、权限或资源缺失无法继续报 `BLOCKED`。主动中断写明原因和最后有效位置。报最近实测步数与单位；速率不稳定或总量未知时，ETA 写未知。

## 确认可续跑，再写出新结果

1. 核对最近一个**完整保存并可读取**的 Checkpoint，记录其步数与身份。写入端用项目支持的原子提交或其他可识别完成的机制，保留上一有效版本；可见的临时文件或更新的时间戳不是完成凭据。
2. 在继续计算或覆盖任何输出前，验证 Checkpoint 来源、格式、对应运行、代码、真实配置、数据和相关环境是否兼容。不得静默退回从头运行。遇到不匹配或缺少必要状态，保留原证据并说明；如果目标只是权重初始化，明确标作新的 warm start，不能叫续跑。
3. 用框架的原生恢复路径核对必要字段：例如模型、优化器、调度器、混合精度缩放、各相关随机状态、采样／数据游标以及步数。哪些字段有影响，由实际框架和保存时点决定；例如在梯度累积中途保存时，仅有模型和优化器通常不足。日志记录加载的 Checkpoint、识别到的上次完成步和本次首个实际步。
4. 需要验证续跑能力时，选获准的小样本，比较正常跑完与发生真实中断后从 Checkpoint 恢复的结果。核对起始位置、状态或产物等价性，而非仅看退出码或文件存在。确定性任务可比较完整状态；存在非确定性时，按实验协议事先约定容差与可比条件。对风险相关的失败路径可用错配或损坏样本确认安全拒绝。

P2 的合成 CPU 对照展示了两个陷阱：只恢复模型的进程正常退出，但完整最终状态不同；改变配置后，正确的恢复入口应在写出结果前拒绝。迁移到真实框架时仍需按项目验证实际保存与恢复的字段，不能用合成结果代替。
