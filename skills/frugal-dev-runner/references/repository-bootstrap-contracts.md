# Repository Bootstrap Contracts — Runtime Reference

> 自包含的仓库接入后备参考。仅在创建、接入或实质修复项目 AGENTS／状态时读取相关部分；普通实施任务不必加载。
>
> 权威来自当前用户授权及有效项目 Bootstrap／Plan。本文件不再声称是外部模板的镜像，不依赖资产包中缺失的历史维护来源；它不能覆盖项目已有有效合同。

## 1. 先检查，再决定是否生成

核对真实项目目录、已有文件／用户修改、适用 AGENTS、相关状态、当前和历史 Plan／编号、已批准目标／Decisions，以及实际 Git／环境事实。不得编造命令、分支、生成边界、权限、发布模型或当前实现。

- **新项目**：首个任务须已说明目标、操作／创建路径、冻结边界、必要验收及交付。没有本地合同文件时先按自包含 Plan 执行；只有在授权内才创建入口和必要文件。Git 初始化、remote 创建、Push／发布各按授权，不由本参考自动授予。
- **既有项目**：优先复用语义完整的入口和状态结构，保持历史编号、有效版本、工程记录及用户文件。仅在本次接入／修复／迁移授权内补缺或有界合并，不为模板统一重命名、覆盖或重建。
- **Bootstrap seed**：保留有效目标、不变量及决策依据。当前代码证明旧实现快照过期时可据权限修正；未实现不等于目标撤销，改变已批准目标仍需相应决定。
- **冲突／缺失**：说明来源、版本、条款和影响。自包含 Plan 足够支持的工作可继续；无法确定必要授权或验收时暂停受影响动作，不猜测。

所有引用的运行依赖必须实际可读。当前文件里的结构说明不是要求创建占位文件，未来路径不能写成已存在。接入后逐项核验入口和必读合同内容，再报告已落地；ChatGPT 上传、聊天建议和全局候选源文件都不算本地生效证据。

## 2. 本地合同入口

基本授权和验收不依赖 Skill 是否触发。项目 AGENTS 或当前自包含 Plan 直接提供必要规则，或指向实际存在的项目合同；后续任务定向加载与当前工作有关的内容，不读整个孵化器。

初始自包含 Plan 应带入当前任务身份／基线、权限与允许路径、冻结约束、推荐／委托、必要验收与证据、输出／数据边界、Git／外部副作用及交付／回传合同。不能仅写“见 ChatGPT 附件”；需落地合同的内容必须在任务中提供或来自执行器可访问的完整来源。

AGENTS 保持短小，按实际项目填写以下职责，省略无关项和空字段：

- 项目身份、工作区与任务匹配条件；已有规则／状态／Plan 的真实路径及必要读序。
- 允许／保护的编辑、数据、生成物和输出边界；用户修改与 Canonical Baseline 的保护。
- 权限及验收／交付合同的具体位置；只读、实验、Git、外部操作不可互相推导。
- 已核实环境与命令语义，包括必要验证命令内部已包含的 compile/typecheck/build，避免重复；未知项明确待核实。
- 实际分支／remote、提交推送政策、部署触发条件与发布授权；仅适用项目写版本、CHANGELOG、线上端点和 smoke 语义。
- 项目特有不变量、停止条件，以及确有必要的专项规则入口。

可把通用底线用几句写清，不能因认为它“属于 Skill”就遗漏保护与必要验收；也不复制 Runner 算法、CI 流程或 UI／PWA 完整检查表。只有实际适用且可访问的专业方法才需列入口，不强制全套 Skill 路由。

Lightweight 可把目标、治理与状态放在已有 AGENTS／README；Standard／Research-intensive 可按需要拆分。新项目若选择 `docs/project/` 或其他目录，必须由实际任务授权并核实，不能将示例路径当统一契约。

## 3. 长期状态职责：可以合并文件

以下名称仅说明职责；沿用项目真实命名和位置，不默认生成三份空文件。

### PROJECT_BRIEF：稳定意图与边界

保存批准的目的、适用对象／场景、优先级、长期不变量、non-goals 及稳定技术／数据边界；当前任务、开发流水和尚未实现的设计不冒充现状。只有这些稳定内容发生获准的实质变化才更新。

根据类型选择有用字段：

- 软件／工具／CLI／后端：核心行为、接口／使用方式、运行平台；适用时补持久化、外部服务、部署、离线、隐私、版本与 UX 基线。
- Agent／竞赛：工具与权限、基线策略、评测协议、规则／截止条件、预算、提交边界及标签可见性。
- ML／研究：研究问题、合法数据／分割、指标／真实基线、可复现条件、路线判定与停止依据。

阶段由项目实际决定。例如软件可用探索／原型／稳定／生产，研究可用假设／基线／对照／结论；不要求采用示例，不把研究结果套入固定四阶段软件生命周期。

### DECISIONS：长期决定与原因

只记录会约束未来任务、有真实替代方案，或遗忘理由会重犯旧问题的决定。普通 bug、任务完成、commit 或临时实现细节不进入；保留 superseded 历史和既有编号。

一条记录可包含：现有 ID／标题、实际状态与日期、采用的方案、事实／约束与替代方案、收益／成本、重审条件及被替代决定。尚未接受的候选明确标识，不冒称 Accepted。项目已有状态词按其合同沿用。

明确委托且在范围内的技术决定可由 Codex 记录理由；研究路线正式接受、重大目标／范围变化、阶段推进、主线合并及新重要方向按 Main／用户既定权限决定，不能借写状态文件扩大权限。

### CURRENT_STATE：真实实施快照

按实际类型记录有用事实：当前代码／配置／分支或实验 run／数据／评价身份、已验证能力及证据来源、未验证／部分实现、环境限制、已确认故障、风险／阻塞、当前工作与下一入口。阶段字段标明最近被主线接受的状态，候选结果与待审查事项分开。

软件发布／线上版本只在适用且有证据时填写；实验指标、失败结论、参数与运行条件放在适当实验记录并链接。无 Git 时不编造 SHA；不要写整个命令流水、历史 SHA 清单或临时失败日志。

状态维护获授权且事实 material change 时，Codex 在同一任务收口前更新必要快照，与本次改动一起交付；不以执行成功为前提，也不一律等下一轮审查。保留 Main 决策字段，不把执行完成自动写成阶段推进。Optional USER CHECK 不成为长期待办；真正持续的证据限制按项目结构记录。

## 4. 工作区、证据与环境

先核实命令 CWD、默认输出／解压位置与临时目录，保护父目录、其他项目、用户改动及未知来源文件。按内容价值区分缓存和证据；有复现／交接价值的 temp/generated/experiment 脚本、候选实现、关键日志及负面实验按许可和体积保留。密钥、敏感／无授权数据、依赖缓存和不适合 Git 的大文件不得机械提交。

清理只针对获准且已确认无价值的内容，不因探索失败删除有效证据或不可重建资产。已验证 Canonical Baseline、合法数据／实验边界、用户 UX／真机偏好和技术约束不因接入模板被迁移或弱化。

优先复用已验证 canonical 环境与仓库命令语义；重要环境结论存入已有适当记录，注明触发条件、确认原因／失败办法、可靠替代及适用范围。不为普通错误造日志或另建知识平台。并行 Worktree 只隔离代码检出，必要时另行协调端口、数据库、可写配置、输出及运行环境，不统一要求容器、DVC 或大型实验平台。

## 5. 交付与回传

正式 GitHub 工程 Plan 通常要求授权范围内的 focused Commit、Push 到明确 remote／分支和真实远端观察。保留有价值的计划、结果与证据；保护用户无关修改。无改动不造空提交，非 Git 项目不为流程自行初始化。

Push 前核实实际目标分支是否触发部署，未获该副作用授权时暂停相应 Push 并报告缺口；仅已授权的安全分支可替代。Push 不等于 Merge，Merge 不等于 Deploy／Publish；分支同步和命令成功不等于主线接受结论或验收通过。必要 Push／核验未完成时准确报告，不能用本地 Commit／tracking ref 证明远端同步。

回传遵循当前项目／Plan 合同；没有正式合同而确需后备时，才读同目录 [handoff-contracts.md](handoff-contracts.md) 的相关部分。此引用可在本 Skill 内访问，不要求新项目复制该 Reference。不要重新定义任务状态、验证标签或冻结／推荐／委托语义；有效负面实验和执行失败按当前任务合同区分。

结果文件记录任务事实与已确定的基线／证据，不含自身最终提交 SHA 要求。最后 Commit／Push 后在对话回执报告最终 SHA、实际远端观察和工作树；不循环 Amend。仅报告真实写入、运行和远端状态，未执行的安装／发布／阶段接受不能宣称完成。
