# Task Handoff｜正式交接、多输入与旧合同

项目有效合同优先。本参考用于实际需要正式回传、协调多个输入或兼容旧约定的任务；普通任务直接对话收口。

## 接收一个或多个 Plan

用项目、任务 ID、实际修订、来源和基线识别输入；缺少历史修订时如实注明来源。明确必须保留的约束、授权与验收，执行其余可自主决定的实现。未授权的新目标、Git／发布、数据操作不由交接推导。必要资料实际可读取，或由任务输入提供足够内容；不依赖未提供的 ChatGPT 附件。

Hub 先查看共同依赖、重复工作、写入范围与共享资源。共享工作可执行一次，分别对应各任务的验收及证据。隔离输出、环境依赖、实验 ID 和共享算力后才并行；不兼容的评价协议保留各自结论。遇到同 ID 不同内容、授权冲突或硬约束冲突时，说明来源和影响，只暂停依赖该项的工作。用已有项目状态留下当前路线／ID 与修订、证据、未决依赖和下一步，后续对话可接手。采用新默认的项目由用户保存正式 Plan，项目不保留副本或专用目录。

## 1. `TASK_RESULT` contract

通常用对话回执简述完成与限制、实际验证、需要的决策及远端交付。正式任务补实际 ID／修订、关键决定与必要证据；研究任务注明可比条件、偏差和停止依据，保留足以追溯的证据入口。主要汇报可引用已授权的阶段报告或必要产物。缺少必要验收或远端交付就标明缺口；非阻塞体验建议不能替代。区分任务完成、证据接受和阶段推进。

若旧项目明确要求 `MUST / SHOULD / HINT`、`FROZEN / RECOMMENDED / DELEGATED_TO_CODEX` 或 `TASK_RESULT`，保留实际语义和所需字段。硬要求继续遵守，建议按有效合同处理，线索或技术委托不扩大操作范围。采用旧四态时：`COMPLETE` 表示必要工作、验收与约定交付均完成；`BLOCKED` 是必要前提不可得；`FAILED` 是实际执行后最终未达标；其他未完成报 `PARTIAL`。以实际项目定义为准。必要时区分 `PASS`、`FAIL`、`NOT_RUN`、`UNAVAILABLE` 与 `NOT_APPLICABLE`；可信负面结论与无效实验分开。

旧项目明确引用本参考的 `TASK_RESULT` 后备格式时，可用原标题 `TASK_RESULT｜<ID> / <Revision 或实际输入来源>`，交代状态、实际基线／分支／工作树、工作与技术决定、硬约束与验收、验证证据、偏差与限制、Git 交付、产物和必要的下一决定；按原合同保留要求的字段名。

项目要求将结果文件入 Git 时，记录任务事实、证据及其已知基线，不回填包含自身的最终 SHA；最终 SHA 和远端观察放在对话回执。没有格式要求时直接说明事实，无需套旧模板。

## 2. `CHECKPOINT_PACKET` contract

阶段评审必要、接收方不能充分读到仓库时，可用简短交接包说明基线、重要变更、验证和证据、风险、已接受决定及待审事项。旧合同若引用本参考的 `CHECKPOINT_PACKET`，可沿用该标题并补对应的仓库、分支／HEAD／工作树、里程碑、重要变化、验证、返工与风险、决策、待审问题及有价值的可选用户检查。路线／阶段总结服务决策和恢复，无需另附常规报告或命令流水。
