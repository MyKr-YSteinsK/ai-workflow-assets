# Project Design Reference｜领域与个人偏好

这是孵化器的按需设计参考，不是所有项目必须执行的统一要求。稳定个人偏好应被认真考虑；与实际项目无关的模块跳过。迁移规则需明确维护位置、适用条件和实际执行入口，并获得相应授权；不能仅因已有 Skill 或完成审查就删除本包仍承担的设计参考。

## A. 跨项目设计倾向

- 核心价值与真实性优先：软件解决实际工作流，实验回答有价值的问题，研究结论具有清楚适用范围。对简历/展示项目，优先追求有证据可展示的工程能力与真实使用场景，拒绝无依据的“企业级”“高性能”等宣传。
- 最小充分的系统：默认避免为了可能的未来需求提前引入微服务、复杂账号体系、通用插件平台、庞大设计系统。重复模式、可观测的规模约束和真实需求出现时再做抽象；实际证据允许例外。
- 已验证成果保护：用户真实使用并认可的组件、性能基线、合法数据/评价基线及关键外部契约，属于需要显式识别和保护的 canonical baseline。改造可能改变它时，说明受影响边界和依据。
- 区分事实与愿景：规划不把实现现状自动当成最终需求，也不把未经验证的愿景写作当前能力。

## B. UI / Web / PWA / App 产品偏好

与交互界面相关时，默认认真考虑以下偏好；不对纯后端/实验/CLI 任务施加视觉规则。

1. **高频操作低摩擦**：关键任务少步骤、易触达；若已有普通工具完成同一事更便捷，应重新审视交互价值。
2. **空间与状态连续**：切换导航、筛选和视图时保留合理位置及上下文，避免随机滚动、黑白闪、突跳和无意义长动画。
3. **动效只解释状态**：没有动画也应可用；不得用动效掩盖加载、布局或滚动问题。
4. **真实目标设备优先**：jsdom、桌面预览、截图只能证明各自范围，真实设备上的操作体验仍需关注。
5. **保护已验证 UI 基线**：已认可的层级、几何、行为，未经明确 redesign 不因全局统一而静默改坏。
6. **共享抽象服务于复用**：不为组件统一而牺牲局部语义、布局和性能。
7. **反馈可见但安静**：保存、下载、同步及加载状态清晰、不过分抢夺内容注意力；可点击与不可点击状态可分辨。
8. **避免模板化 SaaS / AI Dashboard**：视觉身份来自内容、信息层级、排版与目标平台，不默认使用渐变、玻璃卡片墙、徽章/阴影堆砌。

### 可选 UI / 交互模块

- `UI-MOBILE`：真实触摸设备、安全区域、键盘、fixed layer、手势、滚动和 standalone/viewport 边界。
- `UI-CONTINUITY`：切换前后状态与位置连续；首帧与空状态可预测。
- `UI-CANONICAL`：具体已验证组件的用户体验基线纳入项目 UX Contract。
- `ERROR-ACTIONABLE`：错误提示明确失败原因、数据是否安全以及下一步。

## C. 数据、状态和发布可选模块

保留原始模块标识，以减少既有项目语义漂移：

- `RELEASE-LOG`：有用户的长期软件维护语义版本和面向用户的 CHANGELOG；版本反映真实产品变化，发布时点依项目发布策略决定。
- `RELEASE-IDENTITY`：部署版本可追溯到构建/commit/发布身份；CI 绿色不单独证明线上已更新。
- `PWA-UPDATE`：已安装客户端能发现并可靠应用新版，不要求用户清数据/重装；保护历史生产版本的升级路径。
- `APP-DATA-VERSION`：程序/构建版本与独立变化的内容/数据版本分别建模。
- `OFFLINE`：明确必须离线的能力、允许降级的能力及离线恢复边界，PWA 身份不自动意味着全部离线。
- `LOCAL-FIRST`：需求适合时优先轻量本地持久化；账号、同步和云端复杂度需有实质价值依据。
- `DATA-SAFE`：升级/迁移保护已持久化数据，确认失败恢复和旧数据处理路径。
- `STAGED-PROMOTE`：先 staging、完整校验再切换，失败不使半更新结果成为正式事实源。
- `SOURCE-DERIVED`：明确权威源数据与索引、缓存、构建输出等可再生派生产物的区别。
- `DETERMINISTIC-RULES`：权限、过滤、归属等关键确定性规则应可审计、可测试，不交给不可追踪的即时 AI 判断。
- `MISSING-DATA`：缺失、不确定与人工决定显式区分，不能为完整显示编造数据。
- `LIVE-OPS`：影响生产/外部真实状态的操作应有可识别目标和既有授权；常规已授权操作无需每次重复确认，超范围操作另行批准。

## D. 后端 / CLI / 基础设施

关注：真实输入输出与错误路径、可维护的边界、可运行环境、故障恢复、资源/配置隔离、安全与认证（仅真实需要时）、可观测证据。现成基础设施应优先评估复用价值。对 CLI/开发工具，命令接口、帮助/报错及故障诊断体验也是产品行为。

## E. Agent / Skill / 工具调用系统

按任务选择性检查：Agent Loop（输入→推理→工具→状态反馈）、工具/Skill 的实际调用契约、运行时和模型配置、失败与超时路径、状态/记忆、权限与副作用边界、基线运行、策略有效性与任务完成评价。只有证据表明需要多个 Agent 时才采用多 Agent 结构。区分工具注册成功、工具实际调用成功、策略决策正确以及最终任务表现；这些属于不同证据层次。

## F. 数据挖掘 / ML / 竞赛 / 研究工程

按需检查：数据来源与合法边界、任务指标和评价口径、时间/分组/信息泄漏、随机性与实验环境、简单可信基线、可比较对照、训练推断接口、真实部署条件和未知真值。竞争指标与泛化证据分开；失败假设、外部验证、无效实验也可能形成重要结论。实验路线由证据更新，不能用未来标签或竞赛反馈倒灌历史验证。

## G. 可选模块使用规则

用**项目相关性**决定是否引入模块；用户明确偏好被适用项目优先考虑。每个真正启用的模块应转化成当前项目的具体可观察需求、设计约束或风险，而非将本参考全文直接复制入 Project Instructions。已有项目保留有效约定，出现冲突时比较当前用户意图、运行事实与文档版本；不要默默覆盖。
