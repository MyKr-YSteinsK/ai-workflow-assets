# PROJECT_BOOTSTRAP｜项目落地与恢复

用户批准预览后交付可下载的 `PROJECT_BOOTSTRAP` ZIP。它携带项目专属源文件和接入说明。ZIP 是一次性交付；落地并核验后，以项目仓库内的有效文件为维护源。旧项目按已授权范围接入，保留原有有效合同。

## 1. 交付结构

新项目的参考布局如下。按项目需要合并或拆分；项目规模决定内容和职责，不决定固定文件数。

```text
PROJECT_BOOTSTRAP/
  00-START_HERE.md         # 一次性交接：解包、落地与启动
  AGENTS.md                # 供目标项目根目录采用或合并的短入口
  docs/
    PROJECT.md             # 目标、边界、需求和关键决策
    STATUS.md              # 当前实施状态、证据、在跑路线和下一步
    RUNBOOK.md             # 环境、数据地图、运行及故障经验；可合并
    PROJECT_INSTRUCTIONS.md # 仅使用 GPT Project Main 时，供粘贴
```

- **稳定项目合同**：用户批准的目标、需求与验收、重要决策及理由、技术背景与治理边界。重大项目可单独保留 Requirements、Decisions 或 Technical Context；按需拆出 UX 基线、实验协议或阶段报告。已确认需求与当前实现事实分开。
- **恢复上下文**：状态标明可核实的当前基线、已知证据和限制、当前路线和下一入口。尚未核实的配置标作待核实。环境、数据与运行建档按 [工程治理](06-ENGINEERING_GOVERNANCE.md) 选取；稳定命令、配置和锁文件用引用，避免四处粘贴。
- **运行约定**：按 [Plan 规范](05-CODEX_PLAN_SPEC.md) 和工程治理提炼项目真正需要的差异，例如编号规则、主线职责、数据边界和必要验收；写进已有项目文档相应章节。仅当内容确需独立维护时拆文件。正式 Plan 默认以 Issue 交接。孵化或初始化时可在项目约定中记下获授权的仓库外 Plan 目录和命名习惯；无需现在创建目录。无约定则无需保存副本。Plan 正文不随 Bootstrap 迁入项目。
- **GPT Project Instructions**：用 [Architect 基线](04-DEVELOPMENT_ARCHITECT_BASE.md) 编译可直接粘贴的短文本，写明项目身份、当前权责、实际可读的文件与按需加载顺序。使用用户实际的产品约束校验长度；未知时采用 8000 UTF-16 单元作为设计预算。Codex Native 无需为未使用的 GPT Project 生成专用指令。

根 `AGENTS.md` 直接给出项目目的、重要风险／授权边界、恢复必读项和任务合同位置。其中只放每次都要用的规则，完整内容通过实际存在的项目内路径引用。引用写成目标目录结构下可解析的相对路径；移入既有结构时一并修订。生成文件只依赖随包交付并计划落地的内容，或目标项目已有的可读文件；不要沿用指向孵化器通用源文件的链接。

## 2. 从 ZIP 落到项目

1. `00-START_HERE.md` 标明目标路径（或待确认项）、选择的工作入口、已批准的目标与基线、首个任务及授权、包内文件与实际落地位置。分别标记已存在和待创建的文件；若用户尚未批准目录或操作，保留为待确认。
2. 用户可将包解压到 Codex 可读的位置，并交付目标根目录和本次授权。已有项目先读取真实 AGENTS、有效合同、当前状态、分支和用户改动。新项目的项目专属有效源文件落到目标 `docs/`，实际根 `AGENTS.md` 按授权创建或合并；不把交接 ZIP、孵化器通用源全文或正式任务 Plan 一起迁入。旧项目的等价合同可留在其有效位置，不为了路径统一而改写。
3. 初始 Codex 任务可以直接由用户给出，也可由 GPT 生成正式 Plan。若本地合同还不存在，任务输入需携带目标、权限、硬边界、验收与首批文件的内容或实际可访问来源。附件或计划中的未来路径不能作为已读规则。Git 初始化、创建远端、推送及发布分别按授权处理。
4. 落地后按真实布局核对 AGENTS 的路径、必读文件及其间引用，并从入口走一次恢复：定位目标和风险、读到当前状态、找到运行命令和数据说明。能写入、能读取、能运行与已推送各自验证；缺少必要授权或来源时说明影响，继续独立可做的部分。

## 3. 持续维护与同步

- 后续 Codex 新对话从真实项目根入口恢复，只读本任务必需的资料。Codex Native 也可直接依据用户目标和现有仓库建立同样的轻量入口，无需再启动一个 GPT 孵化对话。
- 发现实施事实、环境、长期决定或阶段实质变化时，在授权内更新本地有效源；不要用旧 ZIP 或 GPT 摘要覆盖更新的仓库事实。已有项目的旧工作流、编号、研究基线及历史决定保持有效，除非用户授权迁移。
- 使用 GPT Project Main 时，由用户把相应版本的项目文档上传、粘贴项目指令。能确认时注明实际 commit 或修订。用户指定当前有效附件；若有同名源，先确认新对话读到预期正文，再停用旧版。读不到时说明缺口。已在本地写入、已推送及已由用户同步到 GPT Project 分开确认。

交付前核对实际文件清单、文本编码、相对引用及 ZIP 内容。让用户从交接入口知道下一步由谁做、去哪里读取，以及哪些事实仍需 Codex 在项目中核验。
