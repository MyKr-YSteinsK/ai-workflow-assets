# PROJECT_BOOTSTRAP｜正式项目交接合同

PROJECT_BOOTSTRAP 是个人项目孵化器的最终交付物。仅在用户明确批准最终预览后生成可下载 ZIP；它将已批准目标、项目约束和运行合同交给 ChatGPT 规划主线，并规定 Codex 的实际接入方式。交付文件不自动同步到本地仓库，也不代表已经安装任何全局规则或 Skill。

## 1. 按职责组织，按项目复杂度落地

交付应覆盖下列职责，沿用项目已有有效命名与布局。以下是 Standard 项目的参考布局，不是所有项目必须生成的文件清单：

```text
PROJECT_BOOTSTRAP/
  00-START_HERE.md
  01-PROJECT_BRIEF.md
  02-REQUIREMENTS.md
  03-DECISIONS.md
  04-TECHNICAL_CONTEXT.md
  05-UX_BASELINE.md                 # 仅适用项目
  05-EXPERIMENT_PROTOCOL.md        # 仅适用项目
  06-PROJECT_INSTRUCTIONS.md
  07-CODEX_PLAN_SPEC.md
  08-ENGINEERING_GOVERNANCE.md
```

- **Brief**：项目目的、已批准范围、阶段意图与 non-goals；不是当前实现证据。
- **Requirements**：输入／输出、可观察验收与需求优先级 MUST／SHOULD／FUTURE。需求优先级不等于技术决策权限。
- **Decisions**：重要选择、真实理由、约束、失效／重审条件，保留有效历史与编号。
- **Technical Context**：已核实技术事实、证据来源、未知项及建议；初始设计不是已实现架构。
- **UX Baseline**：适用时保留已验证 Canonical Baseline、用户确认的体验与真机偏好。
- **Experiment Protocol**：适用时保存合法数据边界、分割／标签可见性、指标、真实基线、预算／停止条件及可比较的运行条件。
- **Instructions、Plan／回传合同、Engineering Governance**：规划主线运行方式与 Codex 执行合同。

Lightweight 可合并 Brief／Requirements／Decisions／Technical Context，Plan 与治理合同也可合并进一个有实际内容的文档；用于粘贴的 Instructions 保持可直接使用。Standard 或 Research-intensive 仅按实际需求拆分状态、Plan、实验协议及证据。不给无内容职责造空文件，不要求所有项目采用固定目录或软件产品四阶段。

一个稳定事实尽量只有一个维护位置；其余文档用真实引用，当前 Plan 提取本任务必须遵守的硬约束。交接入口列出职责的实际路径／章节，不保留指向未生成文件的占位引用。

## 2. 两端分别交付什么

### ChatGPT 规划主线

- 用 [Development Architect 基线](04-DEVELOPMENT_ARCHITECT_BASE.md) 生成项目化的 `06-PROJECT_INSTRUCTIONS.md`，包含项目身份、有效合同入口、规划／审查权限和状态责任。Instructions 不依赖未上传源文件、未知 Skill 或历史聊天。
- 用 [Plan 规范](05-CODEX_PLAN_SPEC.md) 生成完整 Plan／TASK_RESULT 合同，新合同保持冻结／推荐／委托、必要验收、状态与证据规则；仅补项目命名、编号及适用研究要求，不另造竞争定义。旧项目保留有效历史合同，只有授权升级时才迁移。
- 用 [Engineering Governance 基线](06-ENGINEERING_GOVERNANCE.md) 提炼适用的目录、输出、Git、数据、状态与发布规则。未知命令、remote、分支、权限保留为待核实，不能编造。
- 将实际生成的文件上传到 ChatGPT Project，粘贴项目 Instructions，明确 Planner 在生成 Plan 前读取有效 Plan／治理合同。参考布局中的 `07/08` 若已合并，入口和 Instructions 均改为实际文档／章节。
- Instructions 按实际产品限制计数；默认检查 UTF-16 code units 并以 8000 为设计上限，实际限制不同时相应调整，不为缩短丢掉关键权限与入口。

### Codex 本地执行端

Codex 必须能从实际适用的项目 `AGENTS.md` 或当前自包含任务入口取得：项目身份与目标、允许的操作／写入位置、硬边界、必要验收、交付和回传义务，以及本任务必读的真实合同路径。仅在 ChatGPT 附件写了规则不算本地接入完成；Runner 未触发时，这些约束仍然存在。

可复用内容按项目需要留在仓库：目标／不变量、有效 Plan／TASK_RESULT 合同、工程治理及必要 UX／实验边界。可以合并进已有 AGENTS、README 或项目文档；不复制整个孵化器、不强制复制 ChatGPT Architect Instructions，也不让每项任务加载全部设计资料。

## 3. START_HERE 的交接入口

`00-START_HERE.md`（或等价入口）实际说明：

- New / Existing / Authorized upgrade 身份、已批准目标与范围、复杂度、当前阶段意图、有效 Plan 命名／编号及下一任务。
- ChatGPT 文件的真实读序与 Instructions 使用方式。
- Codex 目标工作区与当前本地入口；已核实的 remote／分支、已有状态和合同版本。未知项明确标注，不假装已有仓库或本地文件。
- 首个任务允许的读取、创建／编辑、运行、Git 和外部操作；初始化、状态维护、合同合并是否获授权。技术委托不增加这些权限。
- 哪些交付内容当前仅在 Bootstrap 包内，哪些已经核实在 repo；待创建的入口／合同用“计划落地”表述。目标路径未确定时先确认必要路径，不能把默认父目录当授权。
- 交接时可获得的来源／Revision／版本标识及未决冲突，避免把旧摘要当当前事实；不编造缺失的修订号。

## 4. 首个 Plan：本地合同缺失时自包含

Planner 先读取已交付 Bootstrap 与有效合同，不重新进行已完成的需求访谈。生成首个正式、可下载 Plan，明确同一任务的目标及交付边界。

本地合同尚未同步时，Plan 正文必须携带足以独立执行的内容，不能只给“见 07/08／附件”：

1. 任务身份、Plan ID／实际 Revision、目标工作区、来源基线及已批准目标；当前事实与待核实项分开。
2. 操作权限与明确的允许创建／修改路径；运行／输出位置、数据边界、Git remote／目标分支及外部副作用授权按已知事实填写。
3. 实际冻结目标、不变量、Canonical Baseline 和必要 UX／研究约束；推荐与明确委托的技术决定分别说明。
4. 必要验收、实际证据要求、停止条件／Decision Gate；Optional USER CHECK 不替代必要 Gate。
5. 适用的提交、推送、远端核验及回传要求；从当前权威合同带入所需 TASK_RESULT 字段、状态与验证规则，不能仅引用本地尚不存在的返回模板。结果文件不要求包含自身最终 SHA，最终回执在最后交付操作后给出。
6. 准备落地的本地入口与必要合同的实际内容，或 Codex 确实可访问的完整来源和有界合并要求；不能要求执行器从不可见的 ChatGPT 文件猜测生成。
7. 状态维护授权及事实／项目决策的分界；本次可更新的字段与 Main 保留决定分别说明。

自包含 Plan 解决本次访问问题，不撤销已有有效合同。必要权限或验收内容仍缺失时，Codex 报告具体缺项，暂停受影响动作；已经完整授权且不依赖缺项的工作可继续。

## 5. 新项目接入

尚无仓库时，首个 Plan 基于已批准目标与路径明确允许创建的项目目录、文件和本地入口；初始化 Git、创建 remote、推送及发布分别按授权处理，不由“bootstrap”一词推导。轻量 CLI 可先保持普通文件项目，不为满足流程强行初始化 Git。

执行时先核实目录、已有文件、工具输出位置与允许操作，再只创建本次必要内容。将目标 seed 与已核实实施事实分开；写入可复用合同及本地 AGENTS／任务入口后，逐项检查引用存在、可读、内容完整且与当前 Plan 一致。

入口至少直接写明项目／任务边界、必读的实际合同路径或内嵌合同，以及必要验收和交付规则的位置；路径按真实布局填写，不保留占位符，不仅写“调用 Runner”。后续任务从此入口读取相关合同。完成首次落地后才将对应文件标为“已在本地接入”；若有授权 Git 交付，远端可获取还须实际 Push／核验。

## 6. 已有项目接入与有界合并

先检查现有 AGENTS、相关状态、有效 Plan／Revision、Requirements／Decisions、Git 分支／远端及用户修改。保持编号、工程历史、Canonical Baseline、已批准目标和有效旧合同；未实现的目标不能因此被取消。

将 Bootstrap seed 与当前代码／运行事实逐项对照，仅在授权范围内补缺、合并或迁移：已被当前证据推翻的实现快照可修正，产品／研究目标及用户决定不能仅凭未实现而撤销。实质合同冲突说明双方版本、影响和候选处理；无法从既有授权解决时暂停受影响动作，不擅自覆盖文件或重新初始化。

优先将入口指向已有等价文档，必要时在允许修改的 AGENTS 中补具体引用；无需为模板统一重命名、创建三份空状态文件或迁移全量治理。尚未获准修改本地合同，可先用完整且不冲突的当前 Plan 执行已授权任务，留下准确接入缺口。

## 7. 状态、交付与后续使用

当前实现事实以实际 repo、数据、运行证据及版本为准。状态维护获授权时，Codex 在同一任务结束前更新必要事实并随改动交付；研究路线接受、重大目标／范围变化、阶段推进及主线合并由 Main 按权限审查，重大取舍需用户批准。执行完成、证据接受与阶段推进不能互相代替。

正式 GitHub 工程任务通常聚焦 Commit、Push 授权分支并观察真实远端；有价值的研究脚本、失败证据与阶段产物按体积和许可保存，不机械排除 temp/generated。Push 前识别实际部署副作用，未获相应授权不盲目推送；Push 不等于 Merge，Merge 不等于 Deploy／Publish。无 Git 任务如实交付，不自行初始化。

后续 Plan 明确有效基线、任务必须读取的真实路径和本次权限，避免反复加载全部 Bootstrap。复用已有环境知识、命令语义和状态结构；只把有持续价值的发现沉淀进适当的现有记录，不新增 Registry、自动同步平台或通用实验框架。

## 8. 最终交付检查

- 用户批准的目标／范围未丢失；事实、目标、建议与未知分开，UX／实验协议只在适用时生成，Canonical Baseline 与个人偏好受保护。
- ChatGPT 规划合同自包含；Codex 首次任务即使没有 Runner 也能取得必要授权／验收／回传内容。
- 所有声称已在本地的路径实际存在可读；计划创建的文件与 ChatGPT 上传附件不伪装为现有 repo 依赖。
- 新项目创建与既有项目合并入口明确，不重置历史、不静默升级旧合同、不强制固定文件数。
- UTF-8、Markdown、相对链接、ZIP 内容与 Instructions 实际长度检查通过；提供可下载完整文件，而非示例或需用户猜测的模板。
- 交接说明项目身份、已知限制、新对话使用方式与本地接入状态；完成交接后结束孵化阶段。
