# Codex Plan｜任务交接与结果回传

本规范用于新项目及经授权升级的项目。遵守已有项目的目标、权限、必要验收与交付要求，保留编号和历史记录。

## 1. 什么时候需要 Plan

常规任务直接执行；有多个步骤或动态未知时，可在当前对话中规划。需要跨对话执行、复杂实验或明确的外部交付合同时，使用正式 Plan。按任务复杂度、风险和现场情况选择模型与规划深度，无需例行提供型号或档位建议。

正式 Plan 有项目内可区分的任务 ID；已约定的编号继续使用。合同变化时，同一任务保留 ID、更新 Revision；老任务无 Revision 时标明实际输入来源。并行生成 Plan 可用预先约定的阶段前缀／编号段，或由用户分配 ID；不存在可靠来源时先处理实际重名，不另建 Registry。

GPT 编写正式 Plan 时交付实际可用的 Markdown 文件；若界面不能生成附件，交付完整正文供用户保存，并说明交付形式。用户在项目外保存和交付正式 Plan；Codex 可直接读取用户指定的文件或完整输入。项目内只保留有用的任务 ID／修订、结论与证据链接；不新增 `plans/`、`docs/plans/` 或任何 Plan 存档／副本。

## 2. 交接需要回答什么

无需固定章节。一份 Plan 应足以回答：

- **任务是谁、做成什么**：项目、任务 ID／修订、目标工作区、已知基线、预期结果和必要背景。把待查的路径、依赖、运行状态与已核实事实分开。
- **哪些边界必须维持**：明确数据、范围、风险、输出和外部操作的实际权限。重要兼容约束或已批准的实验协议应写实；不把建议的实现细节当作验收。Codex 在边界内可调整实现、验证、优先级及局部路线。建议可以附理由；技术判断不扩大读写、Git、发布、数据或外部操作权限。
- **怎样验收和交付**：给出可观察的功能或研究判定标准和必要证据。需要时注明耗时预算、停止条件、恢复规则、Git／远端核验及特别回传要求。可选体验建议不能替代必要验收。

必要规则可用真实可读的项目路径引用。尚未落地、无法访问的附件如含必要内容，要把相关条款写进输入或另行提供实际可读来源。以当前用户授权、实际有效的项目合同及 Plan 为依据。条款有实质冲突时说明双方版本、差异及影响，暂停需要该决定的部分；其余已授权工作可继续。

## 3. 多个 Plan 汇入 Codex Hub

先按任务 ID／实际 Revision 和来源识别任务，核对基线、依赖、重合目标、硬约束与共享资源。同一任务以已确认的有效修订执行；输入无法判定新旧或同 ID 指向不同任务时澄清受影响项。共享工作可以只做一次，将证据关联到各自任务；不因为合并执行而合并验收口径。

有前置依赖、重叠写入、互斥资源或不可相容验证时合理串行。可隔离且收益明确时并行。资源、实验可比性与写入隔离按 [工程治理](06-ENGINEERING_GOVERNANCE.md)；跨目标、授权或评价协议的冲突交由有权方决定。在既有状态文档记录活跃任务的 ID／修订、依赖、证据、下一步和重新取得有效 Plan 的线索，例如用户可重交的文件名或获授权的来源。公共仓库省略私有绝对路径。新对话能恢复进度；执行前仍须读取有效输入，或确认实际项目合同已充分覆盖本次权限与验收。否则请用户重交，仅暂停依赖该输入的动作。

## 4. 回传与证据

普通任务用一份简洁的对话回执。正式交接带上实际任务 ID／修订；交代完成情况、关键决定、必要验收与证据、真实交付和仍需处理的限制。研究／高风险任务注明实际基线、环境、实验或发布证据、偏差与停止依据。报告按需放入阶段记录或既有证据目录；无需逐任务结果文件。

明确区分实际通过、失败、未运行、不适用和当前不可获得，并用有效项目合同中的标签（如适用）。有效负面结论可以完成研究任务；数据泄漏、失效协议或缺失必要证据只支持相应的受限判断。必要真机、部署或远端验证缺失时，说明缺口，不能用模拟、其他环境或非阻塞建议替代。完成了实现不等于完成了全部验收与交付。
