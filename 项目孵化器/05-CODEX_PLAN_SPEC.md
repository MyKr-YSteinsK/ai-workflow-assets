# Codex Plan & TASK_RESULT｜双向交付合同

本文件是个人项目孵化器内的统一工程任务规范，也应随 Bootstrap 交付给正式开发 ChatGPT Project。核心目标是：**规划的可信度、执行模型的能力、实际仓库证据与任务授权相匹配**。计划和结果构成一次闭环，不依赖未上传的历史 Skill 或隐藏模板。不得为了格式完整增加冗余文件或内容。

本规范是新项目和明确升级项目的默认合同；已有项目继续使用当前任务明确适用的历史有效合同，不自动迁移、重新编号或改写既有冻结要求。Skill 提供专业执行方法及无正式合同时的后备回传，不能凭自身模板覆盖当前有效项目合同或 Plan 正文。

## 一、Plan 生成前的判断

1. 核查当前任务的目标、已批准范围、GitHub 分支/提交、相关代码与项目状态；获取不到真实仓库时明确不确定项，不编造路径、类名、命令或测试结果。
2. 判断此次交接是否需要正式 Plan。简单操作可直接执行；有跨会话交接、明确工程目标、多个阶段/实验或需证据审查时，生成 Plan。
3. 区分 Implement（目标相对明确）、Investigate/Spike（根因或可行路线待核实）、Explore/Experiment（需比较假设并获得可信结论）、High-risk（安全、迁移、数据破坏、核心状态、发布等）。类型可以重叠，按任务选择适当结构。
4. 选择执行模型，并调节规划深度：**Luna Max 是成本优先默认档**，ChatGPT 尽可能提前完成可靠方案分析；只有少数执行中需要持续动态推理或复杂技术取舍的任务才建议 GPT-6.1 Sol High 等高档模型。若简单任务的风险主要来自可预先澄清的需求，应先澄清而非盲目升级；若低档模型难以承担无法预先规划的关键技术判断，应建议升级。
5. GitHub 是实际开发项目的默认同步方式；先核实是否存在 Git 仓库、真实远端及授权分支。按当前任务和项目治理完成必要交付；非 Git 工作区不为满足合同而初始化仓库，无适用变更不制造空提交，实验分支不自动视为已合并到 `main`。

### 有效合同与实际加载

- 按当前用户授权确定适用的项目合同、Plan 及 Revision；保留未被明确替代的有效约束。遇到实质冲突时，说明冲突条款、版本及影响；无法安全确定时暂停受影响动作，仍可继续不依赖该冲突的授权工作。
- 正式 Plan 必须自身携带必要权限、冻结条件、关键验收与返回要求。ChatGPT Project 中的文件不自动存在于 Codex 本地，不能只写“遵循项目规范”却将关键内容留在不可访问附件中。
- 引用本地规范时使用实际存在且可读的路径，区分已核实路径与待现场确认的位置；不强制统一目录。必须读取的合同缺失时，报告缺失项和实际影响：缺少必要权限或验收依据则停止受影响工作；Plan 已完整覆盖所需内容时可继续，并说明缺失引用，不能假称已读取。
- 本合同不要求 Runner 自动触发；Plan 的必要执行义务与回传要求应在没有加载 Skill 时仍可独立理解。

## 二、三级技术决策权限

| 等级 | 意义 | Codex 权限 |
|---|---|---|
| `FROZEN` | 已批准的目标、范围、验收、合法数据边界、必须保护的行为及其他不可擅改约束 | 必须遵守；与真实事实冲突、不可实现或发现重大问题时，报告影响与建议，不静默绕过或假装完成 |
| `RECOMMENDED` | Planner 经充分分析、有明确依据的技术路线、设计、分解和实施建议 | 认真评估；可以依据实际代码、环境和验证证据优化，说明重要偏离及影响 |
| `DELEGATED_TO_CODEX` | Planner 明确委托的、依赖真实代码、环境、实验或动态推理的技术判断 | 在既定权限、范围和验收内自主调查、比较和实施，回传关键决定与依据 |

项目需求的 `MUST / SHOULD / FUTURE` 是**产品范围**，与此处的技术权限分开；已批准的 MUST 可映射为本次 Plan 的 `FROZEN`，不意味着所有实现细节必须冻结。不得把不确定的 `RECOMMENDED` 写成硬性必达的内部 API/Helper/Class/算法。若确有兼容性合同、确认根因或公开接口，则可以精确指定实现约束。

已观察到的实现、类名或环境状态是需要核实的事实，不自动成为冻结目标。`DELEGATED_TO_CODEX` 只委托技术判断，不额外授予文件写入、网络访问、Git、部署或项目目标修改权限。

### 旧合同兼容

旧 `MUST / SHOULD / HINT` 或其他约定按当时有效合同的实际语义解释，不做字符串替换：硬要求继续保护；SHOULD 的可调整条件遵循旧项目合同；HINT 只提供调查线索，不自动构成技术决策授权。不得因新合同发布而改写旧 Plan、命名、编号、已批准约束、实验结论或治理状态。新旧条款实质冲突时，依当前任务明确授权的有效合同判断；不能确定时按上述冲突处理规则报告，不自行解除冻结条件。

### 按模型调整 Plan 深度

**Luna Max 常规任务**：Planner 尽可能提前完成可信技术分析，提供清楚目标和边界、关键输入输出与预期行为、有依据的实施建议、已知依赖和主要失败模式、必要验证与验收，以及待现场确认的未知项。不要把可在规划阶段可靠解决的问题全部推给 Codex；允许 Codex 解决执行中真实出现的局部问题。不得为降低推理难度而伪造路径、接口、环境或结论，也不将 Plan 写成臆测详图或无意义的逐命令脚本。

**高档模型任务，如 GPT-6.1 Sol High**：给清楚的目标与背景、已有证据、不可突破的约束、决策空间、验收与判断标准、必要的实验比较、停止与回传条件。对根因、架构选择、算法设计等高复杂度决策明确 `DELEGATED_TO_CODEX`，避免 Planner 锁定无法验证的具体实现，保留 Codex 的现场自主推理价值。

每份 Plan 完成后的**聊天正文**必须提供：推荐 Codex 模型与思考档位、简短原因、此次 Plan 的主要任务和关键边界；默认偏向 Luna Max。模型额度/速度的猜测不是 Plan 的硬约束，用户可自行选择。模型建议不强制写入 Markdown 执行合同。

## 三、Plan 命名与可下载文件

正式 Plan 文件名在项目 Bootstrap 时选定一种方案并保持**连续、唯一、可检索**：

- 项目标识式：`<项目标识>-NN-中文任务标题.md`，例如 `Config-08-修复运行时配置解析.md`。
- 阶段式：`<阶段标识>-NN-中文任务标题.md`，例如 `S03-08-MCP运行环境诊断.md`。

新项目若沿用原软件产品编号传统，`00` 用于仓库初始化/接入，随后 `01` 起；采用已有阶段式编号的项目继续原规则。跨对话不重置；修订同一 Plan 保留编号，新任务才编号递增；存在并行任务时使用已明确的不同身份避免冲突；旧项目不追溯重命名。通常两位数字，超过 99 则一致地扩展位数而不产生重名。

任务 ID 与 **Plan Revision** 分开：正文标明当前修订标识，同一任务改变合同内容时更新 Revision，TASK_RESULT 报告实际执行版本；无需另建版本管理系统或强制修订文件名。历史 Plan 未标 Revision 时如实说明，以实际输入文件或其他可确定来源识别版本，不补造历史编号。

**每份正式 Plan 必须真正生成可下载的 `.md` 文件**；不可只在聊天中粘贴模板或声称生成了不存在的链接。Planner 在聊天里简要解释核心任务、风险和模型建议即可，正式执行合同放在文件正文。文件应自足，让 Codex 在当前仓库读取后执行；项目内共享文档可以引用准确路径，但当前关键约束不能只藏在 Codex 无法访问的 ChatGPT 附件中。

## 四、Plan 必要内容及弹性结构

不论类型，Plan 需要能回答：

- **Identity / Base**：任务 ID、Revision、项目、当前已知仓库基线/适用分支、相关事实来源；不知道的明确等待 Codex 核实。
- **Goal**：为什么做、范围内要获得什么结果。
- **Permissions**：实际允许的读取、编辑、运行、文件输出、网络、Git 及外部操作；已知边界和适用合同。权限按任务写明，不因技术委托扩大。
- **FROZEN**：必须遵守的要求、禁止事项、数据边界和不变量。
- **Acceptance / Decision Criteria**：功能/研究结论怎样以可观察证据确认。
- **RECOMMENDED**：已有可靠的方案建议，允许按证据调整。
- **DELEGATED_TO_CODEX**：需要现场深入判断的问题、备选方向和所需证据（按需）。
- **Work & Artifacts**：必要的实施/研究步骤、文件工作区、证据保存位置及不应碰的边界；工作区具体路径以仓库现实为准。
- **Delivery / Return**：哪些验证与交付是必要条件，产物整理、适用的提交与推送要求，以及 TASK_RESULT 必须回应的目标、验收、技术决定和真实交付状态；不能只引用未提供的结果模板。

对于简单任务，上述内容可组合成少数章节；不以栏目数评价 Plan 质量。以下内容只在适用时加入：

- **Investigation**：已知症状、当前诊断证据、待否定假设、需解锁的关键决定；先诊断后修复。
- **Experiment**：合法数据和切分、基线、可比性、评价指标、参数/随机性控制、预计探索预算、退出与停止条件、失败也有价值的结果。
- **High-risk**：破坏性操作、迁移与恢复、升级路径、可能影响的用户数据/生产资源、权限与暂停条件。
- **Multi-branch**：独立分支/Worktree、运行输出隔离、资源竞争和合并/比较规则。

如既有仓库中有更具体的 `AGENTS.md`、产品/研究合同，应在不突破当前用户授权的前提下遵守；冲突要回报具体事实而非假装既有约束可执行。不得在 Plan 硬编码未经核实的本地磁盘路径、模型成绩、接口、当前 SHA 或环境可用性。

### 必要验收与 Optional USER CHECK

必要验收由当前有效 Plan／项目合同确定；`Optional USER CHECK` 只是有明确价值的非阻塞体验建议，不等待、不反复提醒、不进入持续追踪队列，无价值时省略。不能把 Plan 明确要求的真实设备验证、PWA 升级 Gate 或其他必要验证降为可选，除非获得明确批准的替代验收。

普通 UI 任务未要求真机 Gate 时，如实报告自动化及其证据边界，可另附真机体验建议；若必要真机／升级验证不可获得，报告 `UNAVAILABLE` 或 `NOT_RUN` 及原因，任务不能因此写 `COMPLETE` 或该项 `PASS`。不同证据只能证明各自范围，不能用截图、桌面浏览器或 CI 代替明确要求的真机／安装客户端路径。

## 六、TASK_RESULT｜执行后的对应合同

任务收口时，Codex 应给出**一份**可直接复制到 Planner 主线的中文 `TASK_RESULT`，内容与实际执行的 Plan 目标、权限和验收对齐。当前有效项目合同及 Plan 的返回要求是执行依据；本规范提供新项目默认语义，Runner Reference 是兼容后备，不另立竞争合同。轻量任务可合并字段，研究／高风险任务补足证据，不机械填满栏目，不省略重要失败、权限或未完成事项。

1. **Plan Identity / Revision**：任务 ID、实际执行修订和输入来源；无修订标识如实说明。
2. **Execution Status**：本任务按合同的完成状态及判定理由，使用下列四态定义。
3. **Base / Final Working State**：实际项目／工作区、基线与最终分支／提交、工作树及任务范围；非 Git 工作区说明，用户已有修改与本次改动分开。
4. **Work Completed & Technical Decisions**：实际改动文件、实现或实验；RECOMMENDED 的重要调整及原因；DELEGATED_TO_CODEX 的最终选择、依据及影响。
5. **FROZEN Compliance & Acceptance**：冻结条件是否遵守；逐项回应关键目标与必要验收，不以总体进度代替未通过项。
6. **Verification & Evidence**：实际检查、结果、证据位置／来源、对应版本和环境、重要指标、可重复性与局限；没有执行的内容单独标明。
7. **Git / Remote Delivery**：Commit、Push、授权远端与分支、核验方式及观察到的远端 SHA、是否 Merge／Deploy（若相关）；未完成步骤及原因。
8. **Deviations / Limitations**：合同或路线偏离、失败、未验证事项与残余风险；必要验收变更应有批准依据。
9. **Artifacts & Durable Findings**：有价值产物、证据保存／清理、实际写入的状态变化及可复用环境／失败发现，不把聊天建议称为已保存事实。
10. **Next Boundary / Required Decisions**：值得继续的边界或确需用户决定的问题；按需附 Checkpoint Signal 和 Optional USER CHECK，不自动生成下一 Plan 或推进阶段。

### 执行状态与实验结论

| Status | 定义 |
|---|---|
| `COMPLETE` | 本任务必要工作、必要验收及约定且适用的授权交付均已完成 |
| `PARTIAL` | 已有有效成果，但本任务必要工作、验证或交付尚未完成；不满足下面更具体的阻塞或最终失败条件 |
| `BLOCKED` | 必要进展当前依赖不可获得的输入、权限、环境、外部条件或用户决定；写明已完成部分和阻塞项 |
| `FAILED` | 必要工作或验收已实际执行，结果最终未满足合同，且按授权预算／停止条件收口；不是仍可正常修复的一次中间错误 |

优先报告实际决定收口的原因：不可得前置条件为 BLOCKED，已执行且最终不达标为 FAILED，其他未完工作为 PARTIAL；多种情况同时存在时写明各项事实。一个 Shell／工具错误或 CI 非零退出不自动判定 FAILED；可在权限、范围及预算内纠正的失败应先分类、诊断并继续。

实验结论与执行状态分开。正确执行并获得可信的“未超过基线／假设被否定”可以 COMPLETE；按预定判定规则得到“证据不足”也可形成已完成的调查结论，但须说明限制。数据泄漏、协议失效、运行未完成或关键证据缺失不能冒充可信负面结果。保存匹配的数据版本、基线、指标、比较条件与停止依据。

若实现已通过但必要 Push 未完成，明确实现／验证与 Git 交付各自状态，整体不得 COMPLETE：当前缺权限／网络等必要条件时 BLOCKED；尚有可执行的未完交付时 PARTIAL；已执行且按停止条件确认最终失败时 FAILED。必要线上或真机验证同理。缺少非必要体验检查不改变完成状态。

### 验证证据状态

| 标签 | 含义 |
|---|---|
| `PASS` | 检查实际执行，或有效复用的证据明确标注来源与适用条件，且满足该项标准 |
| `FAIL` | 检查实际执行并未满足标准 |
| `NOT_RUN` | 检查适用但没有执行；说明原因 |
| `UNAVAILABLE` | 必要环境、权限、数据或结果当前不可获得；说明无法验证的内容 |
| `NOT_APPLICABLE` | 检查或交付步骤不适用于本任务；说明必要依据 |

允许自然语言表达，但失败、未执行与不可得结果不能放在“已通过”中。启动成功不证明最终指标有效；本地成功不证明线上身份，静态／浏览器／真机／CI 证据各自只支持对应命题。复用证据需核对源码、配置、依赖、环境、产物身份和运行假设的有效范围，不能仅凭文件标签声称有效。

### 建议的精简回传形态

```md
## TASK_RESULT｜<Plan ID> / <Revision 或实际输入来源>
- Status：COMPLETE / PARTIAL / BLOCKED / FAILED
- Branch / Base / Commit / Remote / Working Tree：...
- Changes & Decisions：...
- FROZEN / Acceptance：...
- Verification & Evidence：...
- Deviations / Limitations：...
- Artifacts & Cleanup：...
- Next / User Decision（如需要）：...
```

不要求每个简单任务创建仓库结果文件；是否持久化按任务／项目约定。有结果文件时，对话主结果可引用它，并补充最终交付回执，无需输出第二套竞争结论。UI/PWA 专项证据合并到主结果的验证与限制，Optional USER CHECK 另列且只在有明确价值时提供。Agent 任务附运行时与对局证据，高风险变更附迁移／安全／恢复验证；不以长命令流水替代必要事实。

### 仓库结果文件与最终对话回执

若 TASK_RESULT 需要入 Git，采用以下收口方式：

1. 仓库结果文件保存任务事实、Plan ID／Revision、必要证据、已确定的基线／证据来源提交和结论。**不要求填写包含该结果文件自身的最终 Commit SHA**；可写明最终 Git 身份由交付回执提供。不要预写未发生的 Push／远端核验成功。
2. 将授权任务产物和必要报告提交，完成必要 Push 及远端核验；提交前保护用户无关修改并检查排除边界。结果文件的结论以该次保存时点为准，未发生的交付由回执补全。
3. 最后一次 Commit／Push 后，在同一主结果的对话回执中报告最终 SHA、实际远端核验状态、工作树状态及结果文件路径。无需为把该最终 SHA 填回自身文件而反复 Amend。
4. 若收口期间又发生实际变更，重新核对受影响证据与最终状态。结果文件中的实现／验证来源提交可以与最终提交不同，不能自动宣称最后提交的构建或部署身份已验证。

### Plan 与结果的权力边界

`TASK_COMPLETE`：Codex 完成当前授权工作；`EVIDENCE_ACCEPTED`：Planner 已审查重要事实；`STAGE_ADVANCED`：获得相应授权并实际更新正式状态。三者不能相互替代。Codex 可以提出推荐下一阶段，不能仅凭自己提交了 Commit 就宣布整个项目验收或主线合并。

## 七、GitHub 与产物交付的默认值

存在 Git 仓库且本任务产生适用变更时，按当前授权和项目约定默认完成 focused Commit、Push 到**既定授权分支**并核实远端状态。没有适用变更时不制造空提交；没有 Git 仓库时直接报告实际文件状态，不自行初始化或创建远端。阶段性代码、Plan、报告、可复现结果、有效失败证据和治理文件均可按价值、体积和许可纳入 Git，项目收尾再整理当前无用内容。机密、私密或无合法共享权限的数据、巨型缓存、临时依赖和纯垃圾包不得机械上传。

Commit、Push、Merge、Deploy／Publish 是不同事实与权限。普通 Push 授权不自动允许生产发布、合并或历史重写；若目标分支 Push 会触发部署，执行前核对该副作用是否已包含在当前授权中，不在结果中混称“已上线”。远端核验报告目标 remote／branch、观察到的 SHA 及方式；并行工作导致远端已前进时，应确认预期提交是否被包含，不能只因 SHA 不相等就判定 Push 失败。
