# Engineering Governance｜跨项目工程约束与项目化治理

本文件是项目孵化器内的治理基线。输出 Bootstrap 时，提炼当前项目真正需要的工作空间、Git、证据、实验与发布规则，作为 `08-ENGINEERING_GOVERNANCE.md`。安装在 repo 里的 `AGENTS.md` 应写具体、当前有效的本地事实和安全执行边界；不要在所有层级重复整套规则。当前未核实的命令、路径、远端和权限不能编造。

轻量项目可将治理、状态职责合并进已有文档，交接入口必须指出实际位置。ChatGPT Project 附件与全局 AGENTS 候选源文件不自动在 Codex 生效：项目 AGENTS 或当前自包含 Plan 须直接提供必要授权、硬边界、验收及交付，或指向已存在可读的本地合同。基本约束不能依赖 Runner 自动触发；专项方法按任务需要加载，不把完整工程手册复制到各层。

## 1. 权限与事实

- **用户**：批准目标、重大范围/策略变化及超出既有授权的高风险外部操作。
- **Planner Main**：制定 Plan、审查证据、决定是否接受结果及正式推进阶段。
- **Codex**：在授权范围内自主实现/实验和技术判断；需要修改目标合同时先报告冲突与替代方案。
- **Research / Lab / Review**：只对本任务的结论与证据负责；不能因为分支或实验成功便直接提升全局阶段。

实现在何种状态，以当前仓库版本、数据与运行证据判断；目标是什么，以用户确认的 Requirement / Decision 判断。部署身份、Git 状态与聊天中的进度结论需分别核实。

当前 Plan 使用项目有效合同：新合同的权限分类、任务状态、验证标签和 TASK_RESULT 按项目 Plan 规范，不在本文件另立定义；未被明确替代的旧合同继续有效。存在实质冲突时核对版本与当前授权，报告影响，暂停受影响动作而不静默迁移。

## 2. 项目工作空间是边界

- 识别真实仓库根目录，以及用户实际批准的外部数据、缓存或运行目录。**仓库父目录、同级项目目录不是默认可写区域**。
- 在启动可能产生文件的工具之前，核实其当前工作目录、默认输出/解压位置和临时目录；将脚本、实验输出、工作树、运行时产物放在项目约定或明确授权的目录内。
- 多分支任务按需要隔离 Git Worktree、运行目录、可写配置、端口、数据库与其他共享资源。Worktree 仅隔离代码检出，不自动隔离运行环境。
- 优先复用已验证的 canonical 环境、评价基线及仓库命令语义；保护既有 UX／真实设备要求和用户确认的技术边界，不因接入治理而换基线或扩展产品。资源隔离按实际冲突需要，不统一要求容器、DVC、数据库或实验平台。
- 脚本或框架需要项目外目录时，先判断已有授权或请求必要授权，不自行用 `../` 将输出散落到更高一级目录。

## 3. 临时产物、正式证据与生命周期

将项目产物按实际用途区分：

1. **工作中/临时**：一次性调试脚本、可重生成缓存、临时包、重复日志等，放在有界工作区；任务/阶段收口时清理明确无价值内容。
2. **阶段与复现证据**：可复现脚本、关键日志和参数、真实指标、失败实验的判定依据、候选实现、阶段性结果。**倾向提交 GitHub**，哪怕后续会收口清理，只要它仍有交接和研究价值。
3. **长期事实**：真实能力、重要设计决定、系统环境限制、可复用失败知识和稳定基线，保存在项目适当的受控文档和代码/配置中。

不能为了清洁而删除未知来源的用户文件、其他任务正在使用的目录、有价值的失败证据或无法重建的资产。也不能用“用户希望尽量上传”为由，将 secrets、个人敏感信息、未经授权数据、超大缓存、`.venv`、二进制依赖包或纯临时垃圾塞入 Git。

阶段结束或项目收尾时进行适当整理，清理不再需要的当前文件；注意 Git 删除不自动移除历史中已提交的文件，因此敏感信息必须在首次提交前阻止进入仓库。

## 4. GitHub 为默认云端同步入口

- 明确真实 Git remote、默认/工作分支、可推送 upstream 和现有未提交改动，避免覆盖用户或其他任务修改。
- 代码、Plan、TASK_RESULT 或报告、阶段研究脚本、有效实验结果、状态文档等在适当体积和许可条件下默认随任务 Commit/Push；确无改动不创建空提交。
- 独立一致的变更形成 focused commit；任务结束完成剩余提交并 Push，验证远端目标分支 SHA 是否达到预期。网络失败、权限不足、冲突和大文件限制均需准确报告。
- 禁止未经授权的 force push、history rewrite、危险清理、跨任务覆盖和随意重置。
- 上述默认适用于 GitHub 工程任务的已授权 remote／分支，不授予新建远端、Merge、Deploy 或 Publish 权限。Push 前核对实际目标分支及其副作用；不以本地 Commit 或本地 tracking ref 代替真实远端观察。必要 Push／核验失败时交付未完成，按有效 Plan 合同报告，不能假称已同步。
- `Push` 不等于 `Merge`，`Merge` 不等于 `Deploy／Publish`；分支实验可以各自推送，由主线基于证据决定合并或保留。Git 命令成功不代表验收通过，远端分支已同步也不代表主线接受实验结论。
- 非 Git 工作区按本次任务交付，不为满足普通默认自行初始化。不得误提交用户无关修改；有交接价值的 temp/generated/experiment 文件按内容、许可和体积判断，不按文件名机械排除。
- 入 Git 的 TASK_RESULT 记录事实与已确定的基线／证据，不要求写自身最终提交 SHA；最后 Commit／Push 后在对话回执报告最终 SHA、实际远端观察与工作树状态，不循环 Amend。

### 发布/远端操作模式

- `push-only`：提交与推送即本次交付的远端步骤。
- `push-triggered-deploy`：在 Push 前识别实际目标分支及构建／部署副作用，确认既有授权覆盖部署；未覆盖时暂停该 Push 并报告缺口，不能以默认同步规避发布权限。只有已获授权的安全分支才可作为替代；发布已获授权时，还需对应发布证据才能称作线上成功。
- `explicit-release`：只有仓库规则或当前用户明确授权，才执行 tag/release/publish 等行为；按真实环境验证。

正常已授权的日常操作可直接完成，不反复请求形式化许可；生产数据、不可逆操作和超出当前授权的外部操作需要明确决策。

## 5. 实验/Agent/研究型项目的证据治理

- 为可比较实验固定或清楚记录合法数据集、分割策略、标签可见性、指标、真实基线与相关随机/环境条件。
- 评价不同路线时，优先使运行结果相互可比较；分支之间既要隔离输出，又要避免评估协议漂移。
- 允许负面结果：被否定的假设、无法稳定复现的优势、未满足的评价指标，均可能是有效实验结论。保存条件、证据和停止依据，而非无限保留所有中间文件。
- 高成本实验应有适合成本的预算、停机条件或阶段性判断点；真正无法预判的研究过程允许据事实调整。
- 防止后验真值、实验反馈、测试标签或未来信息进入历史验证。研究假设与证据的适用边界不能被无声扩大。

## 6. 重复排障与经验复用

首次失败可正常诊断；同样方法继续失败时，先识别错误模式、检查假设和改变调查路径，避免没有信息增益的循环。有副作用的操作结果不确定时先查询实际状态，不盲目重复；无副作用的语法、路径或诊断错误修正后可继续，不与真实操作混算。跨任务可复用的重大环境或配置结论应存入已有环境说明、决策或问题记录，最少包括：触发条件、确认的原因或失败尝试、可靠替代方案以及适用范围。不要求每次报错都创建日志，也不强制开一个新知识库。

## 7. 长期状态、Checkpoint 和阶段推进

对持续项目，按需维护：

以下是文档职责而非必须新建的三个文件；轻量项目可合并，已有项目沿用有效结构和编号，阶段与字段按项目类型选择。

- `PROJECT_BRIEF.md`：持久目标、不变量和范围；来自孵化文件的 seed，但不是当前实现证据。
- `DECISIONS.md`：有长期影响的有效技术/产品/研究决定及失效条件。
- `CURRENT_STATE.md`：当前实现、代码／版本、验证、实验运行、环境限制、未完成项、重要阻塞／风险及下一工作入口；注明最近主线接受的阶段及尚未接受事项，实际变更按适用交付权限提交推送。
- 适合项目的实验记录/结果目录、Plan 与 TASK_RESULT：作为证据与执行轨迹，不机械累积为空壳文件。

**实施事实**：状态维护已获授权时，Codex 在同一任务结束前据实际执行更新必要的代码、测试、实验状态、分支、环境限制与已确认故障，同改动一起交付。不一律推迟到 ChatGPT 下轮审查，也不为了凑模板更新无变化字段。未验证、候选结论、未推送或待部署事项明确保留其状态；只在实际写入／远端观察后声称相应同步完成。

**项目决策**：研究路线是否正式接受、阶段推进、重要目标／已批准范围改变、主线合并和启动新的重要方向，由 Planner Main 按既定权限审查；重大取舍仍需用户批准。有写入权限的工具实际落地已批准决定，不在聊天中假称改过 repo。明确委托的范围内技术决定可由 Codex 记录理由，不扩大为项目批准。事实更新不得顺带改写主线保留的决策字段。

`TASK_COMPLETE → EVIDENCE_ACCEPTED → STAGE_ADVANCED` 表示执行、证据接受与阶段决策的责任区别，不表示每个任务须形成三份审批单。小项目可由同一主线对话承担多种职责；有效负面实验可完成执行任务，但研究路线接受及阶段推进仍需相应判断。

临时 Plan 或一次 TASK_RESULT 不自动成为长期事实源；重要决定及可复用事实应以最小必要幅度进入已有适当文档。发生冲突时先核对版本与有效权限，不以过期快照覆盖较新的状态。Checkpoint Review 由里程碑、重大架构更改、重复返工、重要风险或研究方向收口等信号触发，不定期强制审计。

## 8. 使用已有 Skills

可以调用已安装并且确实匹配任务的 Codex Skills；所有 Skills 均须服从当前用户授权、真实仓库约束与有效 Plan。Runner 承担专业执行方法，UI／PWA 等承担专项验证；基本授权、必要验收和回传合同直接来自项目入口／Plan，未触发 Skill 也不能忽略。项目 AGENTS 无需固定列出所有 Skill 路由。保留专项流程、Canonical Baseline 与个人 UX 偏好，不借治理接入删除、迁移或自动覆盖既有规则。
